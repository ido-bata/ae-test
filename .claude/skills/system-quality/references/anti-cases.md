# 事前に適用するアンチケース

規則は、適用条件・要求の根拠・反例・排除方法を結び付けて対象へ具体化する。下表は共通の出発点であり、言語・ドメインの既存解析規則を置き換えない。対象固有の規則はその意味を所有するコードと検査に置く。

| ID | アンチケースと反例 | 排除する条件・修正 | 機械的保証の境界 |
| --- | --- | --- | --- |
| R1 | 必須の複数利用者対応を単一利用者へ縮小する | 要求由来の操作列・入力範囲を実装前に固定し、比較対象に共通適用する | ケース通過は全入力の証明ではない。要求解釈自体の忠実性は別責務 |
| R2 | 内部APIが既存というだけで維持し、局所パッチに限定する | 外部互換性の根拠と内部慣例を分離し、要求から別構造を構成する | 差分サイズや変更ファイル数では判定しない |
| R3 | 「最小構成」「今回は不要」で受入条件を削る | 必須条件の削除・任意化を契約変更として扱い、候補自身で承認させない | 文言一致では意味の保存を保証しない |
| S1 | 導出値を保存し、同期用分岐・タイマーを増やす | 履歴・性能要件を確認し、可能なら所有状態と導出へ統合する | キャッシュが必要な場合は無効化と整合性を別に保証 |
| S2 | 同じ業務規則を複数箇所で独立更新する | 規則の所有者を定め、利用側の独自判断を移行・撤去する | 似た構文だけで異なる意味を統合しない |
| S3 | 例外を握り潰し成功値へ変換する | 必要な失敗意味を境界で保持し、エラー入力で検証する | 意図された回復・縮退まで一律禁止しない |
| S4 | 呼出順をコメントで指示し、不正状態を構成可能にする | 有効な状態・遷移を型やAPIに反映する | 型で覆わない外部入力・永続化経路も検証する |
| S5 | 正規境界を迂回し内部状態や別実行領域へ依存する | 所有・依存方向を解析可能にし、必要な操作を正規境界へ移す | importの別名・再export・動的経路は解析器の対応範囲を確認 |
| S6 | 新抽象化を追加し旧方式・移行用分岐を放置する | 利用側移行と旧経路削除を同じ改善の完了条件にする | 必要な外部互換性は移行条件とともに維持 |
| S7 | コメントで回避策を正当化し、根本の不整合を残す | 説明が補っている状態・責務・順序の問題を修正する | コメントの全面禁止や説明文分類だけでは根治しない |
| V1 | 実装に合わせて期待値や前提を弱める | 承認済み契約を候補から独立して照合する | 意図された仕様変更は別の根拠・判断を必要とする |
| V2 | 検査対象から新しいscript・Skill内コード・設定を落とす | 全構成要素と必要解析の対応を確認し、無分類を失敗にする | ファイル列挙は必要解析の意味的完全性ではない |
| V3 | timeout・crash・未実行を拒否成功として数える | baseline成功、固有診断、正常な違反終了を別々に確認する | 既知ケースの拒否は違反クラス全体の完全性ではない |
| V4 | モデルの証明を、対応未確立の実コードへ移す | 実装意味論との対応・前提・成果物identityを検証する | proofの存在だけで適合は成立しない |
| V5 | Lint合格、反例未発見、候補内最良を全体最適と呼ぶ | 要求充足・改善・探索範囲・Optimalを分離する | 比較関係や候補範囲の無断縮小を認めない |
| P1 | Skillの正本・参照・配布先で異なる指示を維持する | 責務の所有を定め、利用箇所を移行し古い指示を削除する | link検査は意味上の矛盾の証明ではない |
| P2 | 検査とともに抑制・除外・期待値を変えて自己合格する | 信頼された契約revisionから検査し、規則変更を独立に評価する | 同じ権限でgateを変更・迂回できる環境は強制未成立 |

全項目を「確認済み」と記録することを成果にしない。排除できたものは実構造と検査で示し、判断に残るものは具体的候補・反例で評価する。必須の未成立条件は説明で相殺しない。
